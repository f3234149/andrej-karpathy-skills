## 工作规则

### 1. 编码前思考

**不要假设。不要隐藏困惑。呈现权衡。**

- **明确说明假设** — 如果不确定，询问而不是猜测
- **呈现多种解释** — 当存在歧义时，不要默默选择
- **适时提出异议** — 如果存在更简单的方法，说出来
- **困惑时停下来** — 指出不清楚的地方并要求澄清

### 2. 简洁优先

**用最少的代码解决问题。不要过度推测。**

对抗过度工程的倾向：

- 不要为一次性代码创建抽象
- 优先沿用仓库中已有的模式、工具函数、组件和抽象。
- 对于较复杂代码应抽取到公共类或公共方法，提高可复用性,以及主线业务逻辑直观
- 不要为不可能发生的场景做错误处理
- 如果 200 行代码可以写成 50 行，重写它
- 不要随意引入新依赖；确有必要时，应说明原因。
- 非必要不扫描node_modules、dist、build 等不需要的文件夹

**检验标准：** 资深工程师会觉得这过于复杂吗？如果是，简化。

### 3. 精准修改

**只碰必须碰的。只清理自己造成的混乱。**

编辑现有代码时：

- 不要添加要求之外的功能
- 不要"改进"相邻的代码、注释或格式
- 不要重构没坏的东西
- 如果注意到无关的死代码，提一下 —— 不要删除它

当你的改动产生孤儿代码时：

- 删除因你的改动而变得无用的导入/变量/函数
- 不要删除预先存在的死代码，除非被要求

**检验标准：** 每一行修改都应该能直接追溯到用户的请求。

### 4. 目标驱动执行

**定义成功标准。循环验证直到达成。**

将指令式任务转化为可验证的目标：

| 不要这样做... | 转化为... |
|--------------|-----------------|
| "添加验证" | "为无效输入编写测试，然后让它们通过" |
| "修复 bug" | "编写重现 bug 的测试，然后让它通过" |
| "重构 X" | "确保重构前后测试都能通过" |

对于多步骤任务，说明一个简短的计划：

```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```

## 代码风格

- 使用清晰的命名，避免过度缩写。
- 保持函数易读，避免把过多职责塞进同一个函数。
- 优先使用类型化、结构化的数据处理方式，避免脆弱的字符串拼接和解析。

## 测试要求

- 行为发生变化时，应新增或更新测试。
- 测试应尽量靠近被覆盖的代码或功能。
- 优先测试可观察行为，而不是内部实现细节。
- 涉及 UI 改动时，应检查关键响应式状态，避免文字溢出、遮挡或布局重叠。


## 安全与风险控制

- 不要记录密钥或敏感个人信息。
- 在系统边界处进行数据校验。
- 能用更小权限完成时，不要使用宽泛的文件系统、网络或 Shell 访问。
- 运行迁移、删除数据、轮换凭据或修改生产配置前，必须先征得用户确认。
- 新增加的文件可以自动添加到git版本控制，但是未经用户要求，不要提交、推送、发布、部署，也不要运行破坏性命令。

文档应简洁、准确。优先写具体命令和路径，少写泛泛建议。

## 完成检查清单

结束工作前确认：

- 用户请求的修改已经完成。
- 已运行相关测试、代码检查或构建；如果没有运行，已说明原因。
- 没有故意修改无关文件。
- 已清楚说明剩余风险或后续工作。
